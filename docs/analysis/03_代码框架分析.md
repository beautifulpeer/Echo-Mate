# Echo-Mate 代码框架分析

## 1. 总体框架

从源码角度看，Echo-Mate 可以分成四层：

```text
SDK / 系统层
    ↓
硬件与基础能力层
    ↓
独立 AI / 视觉 demo 层
    ↓
DeskBot 图形整合层
```

更具体一点：

- SDK 负责系统、驱动、镜像
- 公共管理模块负责 GPIO、系统参数、时间、亮度、音量等
- AIChat / YOLO 提供专项能力
- DeskBot 负责把这些能力做成可交互的 UI 应用

## 2. DeskBot_demo 的框架

## 2.1 入口

DeskBot 的入口很清晰：

- `main.c` 初始化 LVGL
- 根据配置选择 framebuffer、evdev 或 SDL
- 调用 `ui_init()`
- 进入 LVGL 主循环

这意味着它是一个标准的嵌入式 GUI 应用结构。

## 2.2 UI 层组织方式

UI 总控在 `gui_app/ui.c`。

这里维护了一个应用数组，每个页面都是一个独立 app：

- HomePage
- SettingPage
- WeatherPage
- CalendarPage
- GameMuyuPage
- Game2048Page
- ChatBotPage
- YOLOPage
- GameMemoryPage
- DrawPage
- CalculatorPage

### 这一层的设计特点

1. **每个页面都能单独初始化和反初始化**
2. **通过页面管理器统一切换**
3. **主界面像“桌面 OS”一样组织图标和页面**

所以 DeskBot_demo 的核心思想是：

> 把机器人功能包装成多个 LVGL 页面应用。

## 2.3 系统参数与硬件控制

在 UI 初始化阶段，程序会加载系统参数，例如：

- 时间与日期
- WiFi 状态
- 亮度与音量
- 城市与天气接口信息
- AIChat 服务端地址、端口、token

如果配置文件不存在，会自动生成默认配置。

这说明它不是单纯的演示界面，而是已经具备了“设备设置保存”的产品化雏形。

## 2.4 ChatBotPage 的特殊性

ChatBotPage 是 DeskBot 里最关键的一页，因为它桥接了 AIChat_demo。

工作方式如下：

1. 页面首次进入时启动 AIChat 应用线程
2. 周期性获取聊天状态
3. 根据状态刷新机器人表情动画
4. 若收到意图，例如 `robot_move`，则直接驱动 GPIO 控制电机

所以这页实际上完成了：

- UI 动画层
- AI 状态可视化层
- 硬件动作执行层

这是整个仓库里“产品感”最强的一部分。

## 3. AIChat_demo 的框架

AIChat_demo 采用典型的 **Client/Server 分层架构**。

## 3.1 Client 端框架

### 入口

Client 入口在 `main.cc`，启动时接收：

- server 地址
- 端口
- token

然后创建 `Application` 实例并运行。

### Client 内部核心对象

`Application` 内聚合了：

- 音频处理器
- 状态机
- 事件队列
- 意图队列
- WebSocket 客户端
- 意图处理器

### 状态机设计

状态包括：

- fault
- startup
- stopping
- idle
- listening
- thinking
- speaking

转换逻辑大致是：

```text
startup → idle
idle → speaking 或 listening 相关流程
listening → thinking
thinking → speaking
speaking → listening 或 idle
任何状态异常 → fault
```

这个设计非常适合语音助手场景，因为说话交互天然就是一条状态流。

### C 接口封装

为了让 C 写的 LVGL 页面也能调用 C++ 写的 AIChat Client，项目专门加了一层 `c_interface`。

这一层暴露了：

- 创建应用实例
- 运行应用
- 停止应用
- 查询当前状态
- 获取识别出的 intent

这是一种很实用的跨语言集成办法。

## 3.2 Server 端框架

Server 用 Python 写，整体是“WebSocket + 服务管理器 + 多种 AI 服务”的结构。

### 入口

`main.py` 完成三件事：

1. 初始化 `ServiceManager`
2. 启动音频发送线程
3. 启动 WebSocket 服务器

### WebSocketServer 做什么

它负责：

- 接收客户端连接
- 校验 token / 设备信息
- 区分文本消息和二进制音频消息
- 把不同消息分发给不同 handler

### 文本消息链路

文本消息由 `TextHandler` 处理，主要负责：

- hello 握手
- 函数注册
- 状态同步

### 音频消息链路

音频消息由 `AudioHandler` 处理，流程是：

1. 解包二进制协议
2. 解码 Opus 音频
3. 做 VAD 语音活动检测
4. 把音频喂给 ASR
5. 生成文字后触发聊天任务
6. 生成 TTS 语音流并回发客户端

### ServiceManager 的作用

它像一个总调度中心，统一管理：

- VADService
- ASRService
- IntentService
- ChatService
- TTSService
- 各种队列
- 停止事件
- 短生命周期任务

所以 Server 端真正的骨架不是 WebSocket 本身，而是 `ServiceManager`。

## 4. yolov5_demo 的框架

这个 demo 的逻辑非常直接，属于经典视觉推理主循环：

1. 初始化 yolov5 模型
2. 打开 framebuffer
3. 打开摄像头
4. 每帧图像 resize 到模型输入大小
5. 做推理
6. 绘制检测框和文字
7. 输出到 LCD
8. 循环运行并计算 FPS

### 适合学习的点

- RKNN 模型加载
- 摄像头输入
- OpenCV 图像预处理和后处理
- 嵌入式屏幕显示

## 5. SDK 的位置

SDK 不是 demo，但它是整个项目能跑起来的基础。

它负责：

- 选择板级配置
- 编译 uboot、kernel、rootfs
- 打包镜像
- 烧录到 SD 卡或 NAND

所以如果你的目标是：

- 改系统启动项
- 改设备树
- 加驱动
- 调 buildroot 包

那就需要进入 SDK 层，而不是只停留在 Demo 层。

## 6. 一句话理解代码框架

### 如果从“产品结构”看

Echo-Mate = SDK + 硬件控制 + 图形桌面 + AI 能力 + 视觉能力

### 如果从“软件结构”看

Echo-Mate = LVGL 前端 + C/C++ 本地逻辑 + Python AI 服务端 + Rockchip 平台能力

### 如果从“二次开发”看

最值得先啃透的主线是：

1. DeskBot 的页面系统
2. AIChat 的状态机与 WebSocket 协议
3. ChatBotPage 如何把 AI 意图变成机器人动作
